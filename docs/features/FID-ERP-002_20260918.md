## 4. CONTRACT

### 4a. `POST /api/capture/extract` — chỉ đọc, KHÔNG ghi DB
Input: `multipart/form-data` — `file` (PDF/ảnh/xlsx/xlsm), `destination`
(`"po"` | `"warehouse"`)

Output (draft, người xem lại trước khi gọi `confirm`):
```json
{
  "ok": true,
  "destination": "warehouse",
  "rows": [
    {
      "travelerNo": "718039",
      "partNo": "11546389-T",
      "poNo": null,
      "potNo": "693",
      "qty": 45000,
      "confidence": 0.92,
      "lowConfidenceFields": []
    }
  ],
  "warnings": []
}
```
`confidence`/`lowConfidenceFields`: field nào OCR không chắc → để trống
giá trị đó (KHÔNG tự đoán, xem AI_POLICY.md §3) + liệt kê tên field vào
`lowConfidenceFields` để UI tô đỏ, bắt người điền tay.

### 4b. `POST /api/capture/confirm` — ghi Postgres, cần xác nhận CCP-1
Input:
```json
{
  "destination": "warehouse",
  "rows": [ { "travelerNo": "718039", "partNo": "11546389-T", "poNo": null, "potNo": "693", "qty": 45000 } ],
  "confirmedBy": "111"
}
```

Nhánh **`destination = "po"`**:
```sql
-- Chỉ upsert Traveler (đăng ký trước), KHÔNG ghi stock_moves —
-- nguyên liệu chưa về thật, chưa có gì để RECEIVE
INSERT INTO travelers (traveler_no, part_no, po_no) VALUES (...)
ON CONFLICT (traveler_no) DO UPDATE SET po_no = EXCLUDED.po_no
```

Nhánh **`destination = "warehouse"`** (transaction, ghi đủ hoặc không ghi gì):
```sql
-- 1. Upsert Traveler (nếu đã đăng ký từ bước "po" thì cập nhật, chưa có thì tạo mới — "vượt cấp" vẫn PASS)
INSERT INTO travelers (traveler_no, part_no, pot_no) VALUES (...)
ON CONFLICT (traveler_no) DO UPDATE SET pot_no = EXCLUDED.pot_no
-- 2. Ghi RECEIVE vào stock_moves (RECEIVE không bắt buộc machine/operator/shift, xem FID-ERP-001)
INSERT INTO stock_moves (traveler_no, move_type, qty, source_station, device_id, created_at)
VALUES (..., 'RECEIVE', ..., 'OFFICE'|'ADMIN', ..., now())
```

Output:
```json
{ "ok": true, "saved": 1, "skippedDuplicates": [], "moveIds": [123] }
```

## 5. RULES
MUST:
  - **Draft trước, ghi sau** — `extract` KHÔNG BAO GIỜ ghi DB, chỉ
    `confirm` mới ghi, và `confirm` chỉ chạy sau khi người bấm nút (không
    có đường tự động nào gọi thẳng `confirm` mà bỏ qua `extract` + màn
    hình xem lại) — đúng CCP-1/AI_POLICY.md §1.
  - **Trùng lặp phải cảnh báo, không tự động bỏ qua hay tự động ghi đè**
    — trước khi `confirm`, kiểm tra `travelerNo` đã có `stock_moves` loại
    `RECEIVE` chưa (destination `warehouse`): nếu CÓ RỒI → cảnh báo rõ
    "Traveler X đã nhận hàng trước đó", người tự quyết có ghi thêm 1 dòng
    RECEIVE nữa hay huỷ (giống hành vi đã kiểm chứng ở AVP_AI
    `TravelerSection.tsx` — không âm thầm bỏ qua, không âm thầm ghi đè).
  - **`destination = "po"` KHÔNG tạo `stock_moves`** — chỉ đăng ký
    `travelers.poNo` trước. Một Traveler chỉ CÓ THẬT (coi là đã nhận
    hàng) khi có ít nhất 1 dòng `stock_moves` loại `RECEIVE` — đây là
    cách phân biệt "dự báo" vs "đã nhận thật" mà KHÔNG cần thêm cột
    status riêng trên `travelers` (tận dụng đúng nguyên tắc `stock_moves`
    là nguồn sự thật duy nhất, xem FID-ERP-001 §5).
  - **`sourceStation`/`deviceId`** trên mỗi `stock_moves` ghi đúng theo
    người đang dùng (OFFICE hoặc ADMIN) — cơ chế xác định danh tính thật
    (session/auth) THUỘC FID-ERP-011, FID này tạm nhận qua tham số request
    (KHÔNG cho client tự khai báo `sourceStation` tuỳ ý mà server tin
    luôn — xem GPT phản biện vòng 2, FINAL_DECISION.md — phải validate
    tối thiểu giá trị nằm trong `('OFFICE','ADMIN')`, chặn `FACTORY` ở
    route này vì Xưởng không được dùng cổng này).
  - **OCR không chắc → để trống, không tự đoán** — field nào
    `confidence` thấp thì `extract` trả về `null`/rỗng cho field đó, liệt
    kê trong `lowConfidenceFields`, UI bắt buộc người điền tay trước khi
    `confirm` (không cho Xác nhận nếu field bắt buộc còn trống — xem Test
    Criteria).
  - `qty` gửi lên `confirm` phải > 0 (khớp CHECK constraint FID-ERP-001,
    nhưng validate sớm ở API để trả lỗi rõ ràng thay vì lỗi SQL thô).
MUST NOT:
  - Không tạo Lot# — trường `lotNo` để trống ở FID này (thuộc FID-ERP-006).
  - Không cho phép `destination` khác `"po"`/`"warehouse"` (Finish Good
    scan là phạm vi khác, chưa thiết kế ở FID này).
  - Không cho `sourceStation = "FACTORY"` đi qua route này (Xưởng không
    có cổng AI, chặn ở tầng API chứ không chỉ ẩn ở UI).

## 6. EXAMPLE
Traveler `718039`, Part# `11546389-T`, Pot# `693` (phiếu mẫu thật `Data/2.
Traveler/TRAVELER SHEETS SEP 9.pdf`):
```
Bước 1 (destination="po", lúc có email PO, CHƯA có hàng):
  extract → draft { travelerNo: "718039", partNo: "11546389-T", poNo: "PO-2026-xxx" }
  confirm → travelers upsert (po_no="PO-2026-xxx"), KHÔNG có stock_moves nào

Bước 2 (destination="warehouse", vài ngày sau, hàng về thật):
  extract → draft { travelerNo: "718039", partNo: "11546389-T", potNo: "693", qty: 45000 }
  confirm → travelers upsert (pot_no="693") + stock_moves 1 dòng RECEIVE qty=45000
```
Edge: Nếu bỏ qua bước 1 (không có email PO trước, hàng về luôn) → bước 2
vẫn PASS bình thường (`ON CONFLICT DO UPDATE` tự tạo Traveler mới nếu
chưa có) — không bắt buộc phải qua đích "po" trước.

Edge: Nhận hàng traveler `718039` LẦN 2 (hàng về đợt 2 cùng Traveler#, có
thật ở dữ liệu mẫu — số lượng lớn chia nhiều đợt) → cảnh báo trùng, người
xác nhận vẫn ghi thêm 1 dòng RECEIVE mới (không phải lỗi, là nghiệp vụ
thật), sổ cái cộng dồn đúng theo append-only.
